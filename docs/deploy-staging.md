# Deploying staging: Render (API) + Vercel (frontend) + Neon (database)

Staging runs the production build with **Stripe test keys** and its **own database and secrets**.
Everything here happens in the providers' dashboards; nothing secret goes into git.

Expected URLs (Render and Vercel add a suffix if a name is taken; use the real ones everywhere below):

| What | URL |
|------|-----|
| API | `https://ph-healthcare-api-staging.onrender.com` |
| Frontend | `https://ph-healthcare-staging.vercel.app` |

Cost: Render **Starter** (about $7/month, always on: reminders, unpaid-cancellation and the job queue
run inside the API process). Vercel Hobby and Neon Free are enough for staging.

---

## 1. Database (Neon)

1. Neon → **New project** → name `ph-healthcare-staging`, region **AWS Asia Pacific (Singapore)**
   (next to the API and the frontend functions; the dev database in US-East costs ~300 ms per query).
2. Copy the **direct** connection string (Connection details → turn *Connection pooling* **off**).
   It looks like `postgresql://…@ep-…ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.
   This is `DATABASE_URL`. The tables are created by the first deploy (`prisma migrate deploy`).

## 2. Generate the staging secrets (on your computer)

Run each line once and store the output in your password manager, **not** in a file in the repo:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
node -e "console.log(require('crypto').randomBytes(18).toString('base64url') + '#A1')"
```

| Output | Use as |
|--------|--------|
| line 1 | `ACCESS_TOKEN_SECRET` (the **same** value goes to Render and to Vercel) |
| line 2 | `DATA_ENCRYPTION_KEY` (keep a backup: losing it makes health data unreadable) |
| line 3 | `SUPER_ADMIN_PASSWORD` (change it after the first login, plan.md 14.3) |

`BETTER_AUTH_SECRET` and `REFRESH_TOKEN_SECRET` are generated by Render.

## 3. API on Render

1. Render → **New → Blueprint** → connect the GitHub repo `ph-healthcare-backend-project`.
   Render reads `render.yaml` (branch `dev-branch-part-6`, Singapore, Starter plan).
2. It asks for every value marked `sync: false`:

   | Key | Value |
   |-----|-------|
   | `DATABASE_URL` | from step 1 |
   | `FRONTEND_URL` | `https://ph-healthcare-staging.vercel.app` (no trailing slash) |
   | `BETTER_AUTH_URL` | `https://ph-healthcare-api-staging.onrender.com` |
   | `ACCESS_TOKEN_SECRET`, `DATA_ENCRYPTION_KEY` | from step 2 |
   | `SUPER_ADMIN_EMAIL` / `_PASSWORD` / `_NAME` | your staging admin (password from step 2) |
   | `EMAIL_SENDER_USER_*` | your SMTP account (same as dev is fine) |
   | `GOOGLE_CLIENT_ID`, `GOOGLE_SECRET_KEY` | your Google OAuth client (step 6) |
   | `CLOUDINARY_*` | your Cloudinary account |
   | `STRIPE_SECRET_KEY` | your **test** key `sk_test_…` |
   | `STRIPE_WEBHOOK_SECRET` | type `whsec_placeholder` for now; replaced in step 5 |
   | `DAILY_API_KEY` | your Daily key (a newly rotated one) |
   | `SENTRY_DSN` | leave empty unless you created a Sentry project |

3. **Apply.** The first deploy builds, runs the migrations, starts and waits for `/ready`.
   The super admin is created on the first start.
4. Check: `https://<api>/health` → `{"status":"ok"…}` and `https://<api>/ready` → 200.
   If the deploy fails, the log names the missing or invalid setting
   (the server refuses to start with weak secrets or an `http://` frontend URL).

## 4. Frontend on Vercel

1. Vercel → **Add New → Project** → import `ph-healthcare-frontend-project`. Project name
   `ph-healthcare-staging`; framework **Next.js** (detected); build command unchanged.
2. **Environment variables** (Production):

   | Key | Value |
   |-----|-------|
   | `NEXT_PUBLIC_API_BASE_URL` | `https://ph-healthcare-api-staging.onrender.com/api/v1` |
   | `ACCESS_TOKEN_SECRET` | the same value as on Render |
   | `NEXT_PUBLIC_SENTRY_ENVIRONMENT` | `staging` |

3. Settings → **Git** → Production Branch: `dev-3`. Then **Deploy**.
   `vercel.json` keeps the server functions in Singapore (`sin1`), next to the API.
4. If Vercel gave the project a different URL, update `FRONTEND_URL` on Render (it is also the
   CORS allowlist) and redeploy the API.

## 5. Stripe webhook (test mode)

1. Stripe dashboard → switch to **Test mode** → Developers → **Webhooks → Add endpoint**.
2. URL: `https://<api>/webhook`. Events:
   `checkout.session.completed`, `checkout.session.async_payment_succeeded`,
   `checkout.session.expired`, `charge.refunded`.
3. Copy the signing secret (`whsec_…`) → Render → Environment → `STRIPE_WEBHOOK_SECRET` → save
   (Render redeploys).

## 6. Google sign-in

Google Cloud console → APIs & Services → Credentials → your OAuth client:

- **Authorized redirect URI:** `https://<api>/api/auth/callback/google`
- **Authorized JavaScript origin:** `https://<api>`

The API finishes the sign-in on its own domain, then sends the browser to
`https://<frontend>/auth/google/callback` with a single-use 60-second code; the frontend exchanges
it server to server and sets its own cookies (the two apps are on different domains).

## 7. Check staging (plan.md 14.6)

- [ ] Home page, doctor list and a doctor profile load.
- [ ] Register with your own email → the code arrives → verify → log in → log out.
- [ ] Log in with Google.
- [ ] Log in as the super admin → **change the password** (14.3) → create a doctor and a schedule.
- [ ] As a patient, book and pay with card `4242 4242 4242 4242` (any future date, any CVC) →
      the payment banner turns to "paid" and the invoice email arrives.
- [ ] Cancel a paid appointment more than 2 hours ahead → refund shows in Stripe (test mode).
- [ ] Start and complete a video consultation; the prescription PDF email arrives.
- [ ] Stripe → Webhooks → the endpoint shows only 2xx deliveries.

## 8. Monitoring

- Uptime monitor (UptimeRobot / Better Stack, free) on `https://<api>/health` and on the frontend
  home page, alerting your email.
- Render → the service → **Notifications**: deploy failures to your email.
- Optional: Sentry projects for the API and the frontend, then set `SENTRY_DSN` /
  `NEXT_PUBLIC_SENTRY_DSN` (see `deployment.md`).

## Rolling back

- **Code:** Render → Deploys → pick the previous deploy → *Rollback*. Vercel → Deployments →
  previous one → *Promote to Production*.
- **Database:** migrations only move forward. To undo one, write a new migration that reverses it.
  Neon keeps point-in-time history (restore the branch to a time before the bad deploy) as the
  last resort.
